## Как пользоваться этим файлом

1. Открыть раздел «Статус» — понять, где остановились.
2. Открыть последнюю запись в «Логе сессий» — понять, что было в работе.

4. Взять следующую неотмеченную сессию, выполнить её, дописать лог.

## Новая сессия: как начать

Контекст предыдущей сессии **не переносится**. Переносится только этот файл,
git и `.venv` на диске. Поэтому новая сессия начинается не с нуля, а так:

**Шаг 1 — убедиться, что всё на месте (30 секунд):**

```powershell
cd C:\Users\karab\Yandex.Disk\automation_processing_1C\Projects\FlatRegister1C_Textual_parallel
git branch --show-current     # ожидается refactor/s0-safety-net
git status --short            # ожидается пусто
uv run pytest                 # ожидается 103 passed, 1 xfailed
```

Если что-то из этого не сходится — **сначала разобраться, потом начинать**.
Чинить тесты, молча передвигая ожидаемые значения, нельзя.

**Шаг 2 — прочитать `Tasks.md` целиком.** Это 5 минут и это обязательное
условие. Плюс бегло посмотреть `git log --oneline -5`.

**Шаг 3 — первое сообщение новой сессии:**

> Прочитай `Tasks.md` в корне проекта и продолжай рефакторинг с указанной
> там сессии. Сначала прогони `uv run pytest` и проверку регрессии, потом
> начинай правки.

Этого достаточно. Пересказывать задачу в чате не нужно: всё, что важно
знать, уже в файле.

**Шаг 4 — перед правками снять регрессию «до».** Команды в разделе
«Проверка регрессии». Без этого нечем будет доказать, что числа не поехали.

### Чего не делать в начале сессии

- **Не менять `config.json`.** Эталон снят с текущими настройками; их смена
  делает каждую сессию полной ложных «регрессий».
- **Не коммитить без спроса.** Коммит — отдельное решение Саши.
- **Не «улучшать» код до задачи сессии.** План идёт по шагам именно потому,
  что S3-S9 переписывают то, что S4 убирает.
- **Не массово менять текст ошибок через replaceAll.** До S4 половина
  совпадений приходится на закомментированный legacy-код в
  `accountosv_processor.py` — ловушка уже стоила одной поломаной сессии.
- **Не выкидывать `xfail`.** `strict=True` означает, что тест упадёт с
  требованием снять метку, когда баг будет исправлен. Это подсказка, а не
  помеха.

## Проверка регрессии — перед КАЖДОЙ сессией

```powershell
# 1. прогон на реальных выгрузках
uv run python tools\regress.py --root "<папка>" --out tools\after_gaz.json

# 2. сравнение с эталоном; код возврата 1 = есть регрессия
uv run python tools\regress.py --assert-no-regression tools\baseline_gaz.json tools\after_gaz.json

# 3. то же для второго набора
uv run python tools\regress.py --root "<папка МЭЗ>" --out tools\after_mez.json
uv run python tools\regress.py --assert-no-regression tools\baseline_mez.json tools\after_mez.json

# 4. и обычные тесты
uv run pytest
```

⚠️ **Эталон чувствителен к настройкам.** Он снят с вашим `config.json`
(`keep_subaccounts: true`, счета 50/51/52/55/57). Если поменяете настройки —
эталон придётся снять заново, иначе каждая сессия покажет ложные
«регрессии».

## Правила, принятые для всего рефакторинга

1. **Строго сохранять поведение.** Любая правка логики обработки сверяется регрессионным
   стендом по реальным выгрузкам 1С. Расхождения в числах — отдельные задачи, не «мелкие правки».
2. **Расхождения не чинить молча.** Всё, что выглядит как баг, но может оказаться
   намеренным поведением (эталон — ручной расчёт бухгалтера), попадает в «Открытые решения».
3. **Сессия 2 — точка невозврата.** До неё проект ничем не защищён: нет тестов, нет baseline,
   нет логов. Сессии 3 и выше не начинаются, пока Сессия 2 не закрыта.
4. **Мёртвый код удаляется, а не комментируется.** Комментарий — это тоже мусор, который
   агент обязан читать.

**Почему денежные колонки были `object`**

`_preprocessor_openpyxl` собирает кадр из строк листа, где ещё лежат текстовые
заголовки 1С, и тип колонки фиксируется по этим строкам до того, как шапка
отрезается. Проверено на 169 обрабатываемых файлах: денежные колонки приходят
как `str` (175 случаев) или `object` (383), **числом — ни разу**. Приведение
через `pd.to_numeric(errors='coerce')` без потерь (0 отброшенных значений), что
и позволило сделать это в конце `process_file`, не трогая предобработку.

**Почему постусловие по счетам/уровням безопасно**

На тех же 169 файлах **ни одна** колонка `ACCOUNT_COLUMNS` и ни одна `Level_*`
не приходит числом. Значит проверка «счёт — не число» не сработает ложно, и
заодно фиксирует, что имена уровней не превратились в числа.

- Суммы карточки и проводок (`Дебет`, `Кредит`, `Сумма`) в `MONEY_COLUMNS` не
  добавлены: в проводках не-УПП `Дебет`/`Кредит` — это **счета**, а не суммы,

  ориентира, но определения идут через `LEVEL_PREFIX`: число уровней в выгрузке

**Почему пришлось заглушить Excel**

Ветка xlwings включается, когда в одной строке шапки собраны все семь
заголовков оборотов — а именно так устроена настоящая выгрузка 1С. То есть
фикстуры оборотов **по определению** поднимают COM. При десятках прогонов
подряд Excel падал с `0x800706ba` (RPC недоступен), и падение выглядело как
ошибка обработки файла. Фикстура `без_excel` подменяет `xlwings` заглушкой,
возвращающей значение ячейки как есть: в тестовых файлах форматирования нет,
значит «отображаемое значение» и есть значение. Настоящая ветка xlwings
осталась непокрытой — для неё нужен маркер `requires_excel` и живая машина,
это отдельная задача.

**Ошибки в фикстурах — по пути выяснено, как строятся настоящие выгрузки**

| Что было не так | Как на самом деле |
|---|---|
| «Итого» считалась вместе с родителем | Итог = сумма только по строкам-листьям; родитель отбрасывается как задвоенный |
| Обороты клались в колонку корр. счёта `62` | Колонка родителя отбрасывается как задвоенная — обороты кладутся в `62.01` |
| Курсив стоял на строках с данными | Курсив означает «промежуточный итог», такие строки как раз удаляют |
| Пустые колонки Excel A/B в фикстуре | Настоящая выгрузка несёт в них знаки «+»/«−»; иначе `dropna(axis=1)` их съедает и шапка съезжает |
| Даты со временем в не-УПП карточке | Не-УПП читает период только по `%d.%m.%Y`; со временем все строки превращаются в NaT |

    `finally`, каждое закрытие глотает свои ошибки; `contextlib.suppress` вместо
    голого `except:`.
  - `_save_combined_results` / `_save_and_open_batch_result`: при сорванной записи
    временный итоговый файл оставался на диске. Теперь убирается, и пользователь
    получает `OutputError` с подсказкой про место на диске.
  - `_open_file`: неудача открытия больше не провал обработки — только запись в журнал.
  - `write_default_config`: ошибка уходила в `print()`, невидимый в GUI. Теперь
    `ConfigError`. `read_config` при этом **не** бросает наружу — иначе невозможность
    создать `config.json` превращалась бы в отказ обработки файлов.
  - `update_config`: был голый `return False` — настройка молча не сохранялась.
    Теперь причина пишется в журнал.

**Решения, принятые по ходу**

1. **Отказ в одиночном файле теперь пробрасывается как есть**, без прежней
   обёртки `ProcessingError(e)`, которая теряла тип ошибки. В пакетном режиме
   отказ, наоборот, не пробрасывается — плохой файл не должен ронять папку.
2. **Один экземпляр обработки вместо двух.** `_process_single_file_consistently`
   и `_process_file_and_record` делали одно и то же, но отказ записывался в отчёт
   только в одном из них. Сверка результатов и отчёта разъезжалась.
3. **Шаблонный метод `process_file` в базовом классе НЕ вводила** (план его
   подразумевал). Он потребовал бы переименовать 12 методов и не давал ничего
   сверх того, что уже делает воронка в `main.py`. Вернуться к нему имеет смысл
   в S7, когда классы всё равно перестраиваются.
4. **Журналирования в дочерних процессах нет намеренно.** Несколько процессов,
   пишущих в один rotating-файл, мешают друг другу при ротации. Трейсбек
   приезжает в родительский процесс строкой внутри `FileFailure`.
5. **Поправила тексты ошибок, ошибочно названные чужим регистром.** В оборотах
   счёта стояло «Анализ счёта пустой» и «Файл не является Анализом счёта 1с.» —
   пользователю показывалось неверное имя регистра. Это текст интерфейса, а не
   логика обработки, поэтому правка не трогает числа в отчётах.

**Ошибка в своей же работе**

`replaceAll` по строке `raise RegisterProcessingError(...)` попал в
закомментированный legacy-блок `accountosv_processor.py:1-894` и сломал файл
синтаксически. Файл откачен через `git checkout` и переделан: правки вносились
точечно, по живому коду. Урок: **массовую замену по тексту ошибки в этом проекте
небезопасно** — почти половина совпадений приходится на закомментированный код.
До S4 (удаление legacy-блока) массовые правки делать нельзя.
